# Cloudflare Workers and D1, deployed with Alchemy

The api runs as a Cloudflare Worker with a D1 (SQLite) database, and its infrastructure is declared with Alchemy. The stack lives in its own app, `apps/infra/alchemy.run.ts`. We chose Alchemy over Terraform or Wrangler because its resources are Effects: the Worker, its D1 binding and its request handler live in one TypeScript program, and the binding that registers D1 on the Worker at deploy time is the same call that returns the typed client at runtime. Nothing has to be kept in sync by hand between a `wrangler.toml`, an IaC config and the handler code.

The trade-off is maturity: Alchemy 2 is a beta built on Effect 4, with a much smaller ecosystem than Terraform.

## Consequences

- `alchemy dev` runs the Worker in `workerd` with a local D1, so local development and integration tests need no Cloudflare account. Deploying does.
- Migrations are generated by drizzle-kit into `packages/database/drizzle` and applied by Alchemy on every `alchemy dev` / `alchemy deploy`. There is no separate migrate step.
- State is local (`.alchemy/`) by default. A team should move it to `Cloudflare.state()` so every machine and CI share it.
- Integration tests use `alchemy/Test/Vitest`, which needs Vitest hooks to run in registration order (`sequence.hooks: "list"` in `vite.config.ts`).
- `apps/infra` owns the stack, the Alchemy CLI scripts and the state; it depends on the apps, never the other way round. A resource a Worker binds to is declared next to the code that uses it (the D1 resource in `packages/database`, beside its migrations), because the Worker imports it for the binding and `apps/infra` importing the Worker would otherwise form a cycle.
